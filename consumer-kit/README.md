# Public Python runtime consumer kit

This directory is the reusable consumer-side half of the public runtime
contract. It verifies immutable producer releases, stages them without changing
producer-owned bytes, compiles a source-selected MEX against the verified CPython
headers, runs GNU Octave host acceptance, records exact binary identity, and
assembles independently verifiable reference packages.

The kit does not solve Python dependencies or build producer runtimes. Runtime
acquisition happens only through the explicit `stage-runtime.py` command. Build,
test, verification, and packaging commands operate on already staged inputs.

## Interfaces

The versioned contracts under `contracts/` define:

- `bridge-build-v1.schema.json`: source selection, target output aliases, and
  exported MEX entry points;
- `consumer-runtime-receipt-v1.schema.json`: immutable producer release,
  archive, embedded manifest, and qualification identities;
- `reference-package-v1.schema.json`: the downloadable package manifest.

The executable tools under `tools/` are intentionally self-contained so this
directory can be vendored by another consumer:

1. `stage-runtime.py` acquires or reuses SHA-256-pinned public assets and
   transactionally stages `core`, `numpy`, or `fenics`.
2. `verify-runtime.py` re-attests an existing staged tree without network
   access.
3. `build.ps1`, `build-linux.sh`, and `build-macos.sh` compile exactly one
   MEX candidate from a validated `bridge-build.json`. The compiler is MSVC on
   Windows, GCC on Linux, and Clang on macOS.
4. `audit-mex.py` checks the candidate export and load-time dependency
   boundary. Linux additionally enforces the glibc 2.17 symbol ceiling.
5. `prepare-test-layout.py` adds the exact candidate, public backend and host
   fixture around an already staged runtime without rebuilding or copying it.
6. `test-octave*.{ps1,sh}` execute the real GNU Octave -> MEX -> embedded
   CPython path twice: repeated calls in one host process and a clean second
   process.
7. `write-qualification.py` binds the runtime receipt, native audit, source
   provenance, GitHub Actions run, and exact MEX SHA-256.
8. `package-reference.py` and `verify-package.py` assemble and verify the
   downloadable reference package without rebuilding anything.

## Build-once contract

For one source revision and target, compile `bridge.mex` once against the
verified core runtime headers. Use those exact bytes for every selected runtime
profile. Every qualification record and package must contain the same MEX
SHA-256. A source, manifest, or toolchain change creates a new candidate.

The public reference build and automated host qualification run only on GitHub
Actions runners. A published package is different: it is already built and may
be downloaded and tested locally with a compatible installed GNU Octave, with no
compiler, source checkout, dependency resolver, or network access after
download.

## Vendoring

A private consumer may copy this directory to
`vendor/python-runtime-consumer-kit/` and record the upstream public revision,
format version, and tree SHA-256 outside the vendored tree. Its bridge sources,
source-selection manifest, tests, runtime receipt, product package, and release
policy remain consumer-owned.

`check-vendored-kit.py` computes or verifies the deterministic kit tree hash.
It deliberately ignores generated bytecode and VCS metadata.

The public reference bridge is a contract probe. Passing it qualifies this
generic consumer path; it does not qualify another application's MEX binary.
